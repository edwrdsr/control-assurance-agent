# Control Assurance Agent

A small Python reference implementation for **evidence-driven security assurance**. It evaluates structured control requirements against fictional system state, investigates missing evidence using a bounded read-only tool, and reviews structural changes between two illustrative standards catalogs.

**[Technical write-up and architecture at edwrdsr.com](https://edwrdsr.com/work/control-assurance-agent/)**

> Status: **v0.1, offline prototype**. It is not a production security scanner, a live NIST monitoring service, an LLM-driven agent, or an attestation of compliance. Every fixture in `data/` is fictional, including the OSCAL-style examples.

## Why this exists

Documentation records what security controls *should* do. Machine-readable configurations and other evidence can help establish what they *currently* do. This project models a simple bridge between the two, while preserving uncertainty and explicit human oversight.

## What it does today

1. Loads local control definitions and a synthetic system-state snapshot.
2. Tests each condition deterministically: `PASS`, `FAIL`, `UNKNOWN`, or `ERROR`.
3. For `UNKNOWN`, performs at most `--lookup-budget` permitted local evidence lookups, then reevaluates.
4. Compares two fictional OSCAL-style catalogs for structural `ADDED`, `REMOVED`, or `MODIFIED` controls.
5. Maps detected catalog changes to sample organization checks and prepares a human review queue.
6. Writes `report.html` and `report.json`, including source labels and tool input/output SHA-256 digests.

In the supplied example, it evaluates **5 controls**: **3 PASS** and **2 FAIL** after retrieving missing backup evidence. It flags **2 sample catalog changes**. No settings are changed.

## Architecture

```text
Local control definitions + synthetic state      Fictional catalog versions
                       |                                  |
                       v                                  v
                 evaluate_controls                    compare_catalogs
                       |                                  |
                UNKNOWN evidence?                      changed IDs
                       |                                  |
                allowed local lookup                 mappings.json
                       |                                  |
                  reevaluate            +----------------+
                       |                |
                       +-------+--------+
                               v
                   report + trace + review queue
                               |
                        human decision
```

The core tests and decision logic **are not generated by an LLM**. The 'agent' is a bounded deterministic orchestrator. A future AI investigator may propose follow-up questions or summarize evidence, but it must not override authoritative control outcomes.

## Requirements and quick start

Python **3.10+**. No third-party packages or API keys are needed.

```bash
python -m assurance_agent --out out
python -m unittest discover -s tests -v
```

Open `out/report.html` after the first command. The program also creates structured `out/report.json`.

To see what happens when missing evidence cannot be investigated:

```bash
python -m assurance_agent --lookup-budget 0 --out out-no-lookups
```

The backup test will remain `UNKNOWN`, not `FAIL` or `PASS`.

## Scope and guardrails

- All inputs come from local, synthetic JSON fixtures.
- No credentials, remote connections, LLM provider calls, or security-setting writes.
- `UNKNOWN` means there is not enough evidence; `ERROR` means a check could not be evaluated.
- Evidence lookups are bounded by an explicit step budget.
- SHA-256 digests make inputs and outputs easier to compare, **but do not provide provenance authentication or cryptographic signatures**.
- Catalog diffs identify **structural differences**, not necessarily meaningful regulatory or compliance changes.
- Human approval is required for subsequent actions; the review queue does not create tickets or modify systems.

## Next engineering milestones

1. Add one genuinely **read-only, scoped integration** to an authoritative system. Normalize fields, log evidence provenance, check freshness, and handle API failures.
2. Build replayable test cases for missing, stale, contradictory, and malicious evidence, plus rate-limit and connector-failure behavior.
3. Ingest **official** NIST OSCAL catalogs with version and source tracking, distinguish editorial from substantive changes, and review proposed mappings.
4. Optionally introduce an LLM-based investigator with a fixed tool allowlist, bounded time/cost/tool calls, prompt-injection defenses, and evidence-cited explanations. Keep `PASS`/`FAIL` deterministic.
5. Add scheduling, alerts, and explicitly human-approved downstream actions.
